# Repository Guide

## Ground Truth

- This is a virtual Cargo workspace on Rust 2021, pinned to Rust 1.89.0. Current code depends directly on Unix sockets, PTYs, and signals, so development targets macOS/Linux and CI gates on macOS, not Windows.
- The canonical test gate needs `git`, and builds need a C toolchain for bundled SQLite. There is no external database service.
- Use `Cargo.toml`, crate-level module docs, `scripts/dev`, and current source as truth. Working plans and historical checkpoints live in a local `plan/` (not published); they can contradict later implementation and are never the gate.
- `docs/performance.md` is the cost model, and it is not optional reading before touching the delta path, the Tauri render path, the core lock, or anything that spawns a process. This repository has rungs a normal request handler does not: per cell (~10 000 per frame), per delta (≤125/s **per attached terminal**), per frame (the whole window). Work priced for a request handler is ruinous three rungs down.
- `docs/architecture.md` is the shortest current system map. Tauri + Solid is the GUI; it connects or starts the daemon and renders a passive `CellGrid`. Daemon `dump`/`stats` are unwired no-ops.

## Commits And Pull Requests

- Subject and body (and PR title/description) must be clear and precise about context and changes: imperative subject, why-first body, no `feat:`/`fix:` prefixes. Full rules in `docs/commits.md`; agent checklist in `.agents/commits.md`.

## Commands

- The canonical gate is `scripts/dev check` (also the default for bare `scripts/dev`): `cargo fmt --all -- --check`, then `cargo clippy --workspace --all-targets -- -D warnings`, then `cargo test --workspace`. CI runs the same gate on macOS.
- Build everything with `cargo build --workspace`; run one package with `cargo test -p <package>`.
- Exact unit-test example: `cargo test -p client --lib ipc::tests::connect_request_and_event_round_trip -- --exact`.
- Exact daemon E2E example: `cargo test -p daemon --test integration end_to_end_shell_session -- --exact`; run all non-ignored E2E cases with `cargo test -p daemon --test integration`.
- Exact terminal golden example: `cargo test -p terminal-core --test golden plain_text -- --exact`. Snapshots live in `crates/terminal-core/tests/snapshots/`; `cargo insta review` requires a separately installed `cargo-insta`.
- `cargo deny check` is a separate policy check. It is not part of `scripts/dev check` or CI, and `cargo-deny` is not installed by the pinned toolchain.
- Cross-machine distribution is `scripts/dist`: `build [--universal]` delegates to the package scripts and emits one self-contained tarball (`dist/release/`, with an embedded installer that strips quarantine and installs into `/Applications`), `ship <user@host>` adds scp, `install <archive>` runs the embedded installer locally. Like the package scripts it is never run automatically; its archives are not the same artifacts as `dist/macos/Forge Node.app`.

## Runtime And Tests

- `scripts/dev daemon` defaults to `run` and uses real per-user config, database, logs, lock, socket, and worktree paths. Use `scripts/dev daemon info` when only inspecting resolved paths/config.
- A second daemon exits successfully when the singleton lock is held, so exit code 0 does not prove a new daemon started.
- `crates/daemon/tests/integration.rs` starts its own daemon with an in-memory DB and temporary socket; do not start a developer daemon for it. It needs writable `/tmp`, a real shell/PTY, and real `git`.
- `git-service` integration tests return early when `git` is absent, so a green package test does not prove Git integration ran; daemon E2E tests fail instead.
- Workspace tests are not fully hermetic: shell-environment coverage invokes the user's login shell, and daemon startup may run `--version` for installed agent CLI candidates.
- Ignored Phase 0 smokes exercise the four real local agents, `vim`/`htop`, reconnect, and latency. They are macOS reference checks; do not substitute Docker for the explicitly deferred Wayland/X11 validation.

## Comments And Code

A comment carries a constraint the types cannot. It is not narration, history, or a second copy of a plan doc. This applies to Rust (`//!` / `///` / `//`) and TypeScript (`/**` / `//`) the same way.

- Write the *why that is not in the next line*: a rejected alternative, a unit, a lock/IO exception, a protocol quirk, a budget. If a reader who knows the language already has it, delete the comment.
- One sentence is the default. A block comment must name a constraint. Essays belong in `docs/` or an ADR, with at most a pointer from the code (`ADR-008`, `docs/performance.md`).
- Do not restate the identifier (`/// All known projects` on `projects`, `/// Create an empty store` on `new()`, `/** The project rail. */` on `SIDEBAR`).
- Do not keep history in comments (`used to`, `the Feature tab could not answer before`, brand-hue archaeology). Git holds that.
- Do not cite old plan section numbers (`§11.5`) as if they were current truth. Point at the type, the ADR, or this file.
- Crate/module `//!` (and a TS file header) is a map: what this module owns, what it must not do, where the rest lives. Not a retelling of `docs/architecture.md`. Two to six lines; the rest is a doc.
- Public `///` / JSDoc is for the *caller*: contract, error, units, non-obvious ordering. Private `//` is for the *next editor*: the trap. Do not paste the same paragraph in both.
- A name beats a comment. Extract a function, a type, or a constant (`RESIZE_DEBOUNCE_MS`) rather than explaining a magic block. Ambiguous pronouns (`this`, `the whole point`) without a referent are a defect — name the thing.
- Tests comment the surprising assertion or the fixture's trap (Solid `createComputed` vs `createEffect`, `navigator.platform` under vitest), not arrange/act/assert.
- Required comments stay required, and stay short, in the same file: every core-lock exception, every `#[allow]`, every recoverable-`unwrap` absence in daemon paths.

Rust: `rustfmt` defaults and `clippy -D warnings` are the gate. Match `#[non_exhaustive]` with a wildcard arm from other crates. Do not `unwrap()` / `expect()` on a recoverable daemon path. `#[must_use]` on pure getters that are easy to ignore.

TypeScript (`apps/tauri`): Bun is pinned in `.bun-version` and the package manifest; `bun run check` runs `oxlint`, `oxfmt`, Vitest under Bun, native tooling tests, typechecks and bundle budgets. `strict` is on; do not add `any`. Bun APIs and types belong in tooling, never the WebView. Theme values come from `src/theme/tokens.ts`, never a hex. A helper with a right and a wrong answer lives in its own module so a test can import it without Solid's server build — that split is the comment, not an essay above the form.

Existing code has a lot of the anti-pattern (file-level essays, field restatements, `used to` history, `§N` citations). Do not copy it. New code follows this section; a touch of an old file is the moment to delete the redundant comment next to the change, not to rewrite the crate.

## Boundaries And Invariants

- `domain` owns shared serializable state and terminal wire types; `protocol` owns transport-independent framing/messages. Protocol enums are `#[non_exhaustive]`, so cross-crate matches need conservative wildcard arms.
- The daemon owns every PTY and the only VT engine. `client` keeps a passive snapshot/delta replica; never add `terminal-core` or a second emulator to GUI code.
- `client::Client` deliberately uses blocking `std` Unix sockets and a reader thread, not Tokio. `Client::request` blocks and must be bridged off the UI thread (Tauri's runtime thread); its event channel is bounded (64) and overflow disconnects so the GUI reconnects for a snapshot. Never block that reader on a full event queue: it also delivers request replies.
- Current daemon orchestration lives in `crates/daemon/src/core.rs` behind one `Mutex<Inner>`. Keep lock order `inner -> registry` and never hold the core lock across `.await`.
- `TerminalRuntime::emit_seq` advances once per emitted delta, not once per engine feed. Preserve this distinction or clients will detect false sequence gaps; bounded daemon queues recover lagging subscribers with a fresh resync rather than replaying backlog.
- One processed PTY batch is one core-lock acquisition: `Daemon::pump_terminal_batch` feeds the engine, optionally emits a coalesced delta, routes the activity note, and advances the idle clock in a single critical section. `pty_loop` waits on `poll` with a deadline (the next frame or a synchronized-output timeout), drains available bytes into a bounded batch, then pumps. Do not sleep after a successful read, and do not split the pump back into feed/`has_subscribers`/emit calls. `FRAME` (8 ms) is the emit floor for an attached terminal, not the read cadence. Unwatched sessions no longer throttle the child.
- `Session::base_commit` **is** a column (migration 9), unlike `terminal_id` and `last_activity_at`: it is resolved once with `git rev-parse HEAD` when the session is created — between two lock sections, never inside one — and never again, because a restart continues the same unit of work. `Db::purge_sessions` still drops the row on startup unless `sessions.persist_history` is set, so it earns its keep across a session's life rather than across a daemon restart.
- `Session::last_activity_at` is runtime-only, like `terminal_id`: never a column, reconstructed as `ended_at`/`created_at` on load. The PTY thread owns the ≤1/s coalescing clock that bumps it, and `SessionUpdated` carrying only a bump is throttled to `terminal::ACTIVITY_BROADCAST`.
- Idle policy lives in `crates/daemon/src/idle.rs` as a pure function of (session, now, attached, warned); the sweeper in `core.rs` supplies those and performs the effects. Inactivity can warn *and* stop; age (`long_running_warn_after_secs`) only ever warns. Nothing stops by default — `sessions.idle_stop_after_secs` is `0`.
- `pull_requests::Cache` holds the last remote pull-request read behind its own `Mutex` on `Daemon`, never the core one — the same rule as `external_agents`, for the same reason: a `gh` subprocess must not serialize PTY work. `GetSnapshot` clones that cache and is forbidden from touching the network; only `RefreshPullRequests` (and a successful `CreatePullRequest`, which invalidates first) may. A `PullRequest` is runtime-only like `Session::terminal_id` and `Workspace::status`: no column, no migration. Eligible hosts are `github.com` plus `[github] enterprise_hosts` — never inferred from remote-URL syntax. `gh api graphql` exits non-zero while still returning usable `data`, so that path parses stdout regardless of the exit code and only fails globally when `data` is absent or empty.
- The GUI's diff view is a *read*, not a subscription: `GetWorkspaceDiff` runs `git diff` locally and answers synchronously like `ListBranches`, so it neither acks-then-events nor broadcasts. `GetSessionChanges` and `GetWorkspaceReview` are the same kind of read against a *base* rather than `HEAD`; `git-service::working_tree_diff` takes that base and, when it has one, sources the file list from `diff --name-status` because `status` cannot see a path a commit changed and left clean. A `WorkspaceDiff` is runtime-only like `PullRequest` — no column, no migration, no `Store` field. `git-service::diff` keeps its subprocess count flat in the number of changed files (one `status`, one `numstat`, one batched `diff --patch` split on `diff --git `); only untracked files cost a process each, through `--no-index`, whose exit status **1** is the success case. A patch over budget is dropped whole and flagged, never cut: half a patch is not a patch.
- The GUI never does `std::fs` on a workspace (ADR-012): `ListFiles` / `ReadFile` / `WriteFile` / `SearchFiles` are local synchronous reads like `GetWorkspaceDiff`, answered by `fs-service` outside the core lock, with every path canonicalized inside the checkout. `FileTree` / `FileContents` / `SearchResults` are runtime-only — no column, no migration, no `Store` field. `WriteFile` requires the `revision` from the last read and refuses with `PreconditionFailed` when the disk has changed (an agent wrote the same path); the GUI re-reads rather than embedding content in the error. `SearchKind::Definition` is a `git grep -w -F` for a string `fs-service` has already validated as an identifier — a symbol that arrives from a click in the editor must never be able to become a regex — filtered by `definition_rank`, which is a heuristic and is therefore *offered* (several candidates) rather than resolved; `SearchResults.query` echoes the question because the answer is an event with no request id. A line to jump to is a standing request in `viewsStore` (`editorReveal`), never part of `viewKey`, so a second jump into an open file moves the caret in that tab instead of opening a rival one.
- A stopped rebase is **read, never remembered**: `git-service::rebase` answers `GetRebaseState` / `ContinueRebase` / `AbortRebase` / `MarkConflictResolved` from the index and git's own state files on every call, and a `RebaseState` is runtime-only like `WorkspaceDiff` — no column, no migration, no `Store` field. Staging a path is what takes it off the conflict list, which is why the GUI re-reads after every action instead of caching a count. `--continue` and `--abort` are local, so they go through `run_git`, never `run_git_network`; `run_git` pins `GIT_EDITOR` and `GIT_SEQUENCE_EDITOR` to `true` because a sequencer command opens `$EDITOR` for the message it already has and would otherwise hang until the ADR-008 timeout. "Resolve with AI" is the ordinary `CreateAgentSession` with an `initial_prompt` (§16.8) — no second kind of agent, no provider branching outside `crates/agents` — and the prompt forbids the agent from running `--continue` itself: continuing the replay stays a human gesture in the Git panel.
- `external_agents::Cache` fronts transcript discovery with a 10 s TTL keyed on a fingerprint of the scanned roots, so `GetSnapshot` is not a filesystem sweep. Adding a project or worktree invalidates it immediately; the TTL only covers re-asking the same question.
- Two usage readings exist and never merge: `ProviderUsage` is the provider's word on a remaining allowance, `UsageAnalytics` is our count of what was spent, scanned off the same transcripts by `agents::collect_analytics`. Token parsing and the model price table live in `crates/agents` like every other provider fact; `daemon::usage_stats::Cache` fronts the scan with a 60 s TTL keyed on the window, on its own `Mutex`, and `GetUsageAnalytics` answers synchronously like `GetWorkspaceDiff` — no ack-then-event, no broadcast, no column. A resumed Claude transcript re-records earlier turns, so turns dedupe on `message.id`; Codex's `total_token_usage` is cumulative, so a turn is a difference. Thinking tokens are output tokens and are never added into `TokenTotals::total`. A model with no published price contributes nothing and increments `unpriced_turns`: the estimate is shown as a floor rather than quietly under-reported, and a bounded scan reports `skipped` rather than looking exhaustive.
- Successful mutations normally return `Response::Ack`; changed domain objects are delivered to all clients through `DaemonEvent` broadcasts.
- Theme tokens are the single source for colors and metrics (`apps/tauri/src/theme/tokens.ts`); views must not hardcode hex values.
- Provider-specific binaries, probes, and launch behavior belong in `crates/agents`; other crates must not branch on provider IDs. Application Git subprocesses belong behind `git_service::run_git`, which enforces locale, no prompts, captured output, and timeout behavior; test fixtures may invoke Git directly.
- Commands that open a socket go through `git_service::run_git_network`, never `run_git`: its own timeout (`[git] fetch_timeout_secs`, default 120 s — a deliberate, documented deviation from ADR-008's single 30 s budget), plus `GIT_SSH_COMMAND` with `BatchMode=yes` and askpass disabled, because `GIT_TERMINAL_PROMPT=0` does not reach `ssh` and an encrypted key with no agent otherwise blocks until the timeout. `fetch` and explicit `push` (only from `CreatePullRequest`, never from a sweeper) use that path. Pull requests are opened *and listed* via the `gh` CLI: `git-service::github` is the one place that talks to a forge host rather than to git objects, and `[github] executable` is what makes that path testable without the network.
- Every request that opens a socket acks when the work *starts* and reports through an event, and coalesces rather than queues: `FetchRemote` → `RemoteRefsUpdated` (`Inner::fetching`, per project), `CreatePullRequest` → `PullRequestOpened` (`Inner::pr_opening`, per workspace), `RefreshPullRequests` → `PullRequestsUpdated` (`Inner::pr_refreshing`, global — one refresh already covers every repository), `DraftWithJuva` → `JuvaDraftReady` (`Inner::drafting`, per workspace). The GUI drains one command channel on one thread and that channel also carries `RuntimeCommand::Input`, so a synchronous network write would freeze typing. A worker that fails to spawn must clear its own coalescing flag.
- Juva drafts commit messages, PR descriptions and change reviews from a workspace's change context (`DraftWithJuva` → `JuvaDraftReady` → editable dialog → `CreateCommit` or `CreatePullRequest`). Commit stays local; only the PR path pushes. `juva::draft` is deterministic and local; `juva::draft_remote` sends the same system prompts to the `[juva]` endpoint behind the `JuvaClient` seam and **falls back to the local draft on everything** — off, unset key, timeout, non-2xx, unparseable body. The key comes from the environment variable `[juva] api_key_env` names and is never stored in the config file or the database.
- `Workspace::status` is runtime-only, like `Session::terminal_id` and `last_activity_at`: never a column, `Default` on load. `measured_at: None` means "not measured", which is not the same as clean — do not render it as clean.
- The Tauri host reaches wire types through `client`'s re-exports (`DaemonEvent`, `ProviderInfo`), never by depending on `protocol` directly.
- A managed worktree is provisioned after `git worktree add` because it lives away from the repository and starts without `.env` and friends. What follows a checkout is a **rule**, not a list (`domain::ShareRule`: `Copy` / `Clone` / `Link` / `Run`), stored per project in `worktree_shares`; a project with no rules falls back to the global `[worktrees] copy` + `setup_script`, synthesised into rules and run through the same engine. Policy is a pure function (`daemon::shares::plan`), effects live in `shares::apply`, and `core.rs` decides which workspace and when — the `idle.rs` split. Provisioning is best effort by design: the checkout already exists, so a failed rule becomes a `Skip` with a note and a failed script a notice, never a refusal.
- **Provisioning never runs on the request thread and never holds the core lock across filesystem or subprocess work.** `CreateWorktree` persists the workspace, broadcasts `WorkspaceCreated` and *starts* the run; the outcome is `SharesApplied`, coalesced per workspace by `Inner::provisioning` and released by a `Drop` guard, like `fetching`/`pr_opening`. A background run never overwrites a path that already exists — only `ApplyShares { only: Some(ids) }`, the user naming those rules, may back up and replace — and `ShareCleanup::RemoveInjected` removes only what is still recognizably Forge's, never the source workspace's own file. `Link` resolves its store through `git rev-parse --git-common-dir`, so no checkout is load-bearing for the others (P4).
- `SpawnSpec.env` is a complete environment, not an overlay: PTY launch clears inherited variables before applying it. Preserve daemon-injected `TERM`, `COLORTERM`, `FORGE_SESSION_ID`, and `FORGE_WORKSPACE` when changing spawn construction.
- A review of someone else's pull request is a **read, twice guarded** (§16.9): the launch carries `read_only`, which applies the provider's own `AgentDescriptor.review` flags *after* a profile's own so they win, and the recipe's prose forbids editing, committing and posting. `CreateAgentSession { read_only: true }` is refused with `InvalidRequest` for a provider that declares no such mode — never downgraded to one that can write — and the daemon remembers it in `Inner::read_only` so a restart re-applies the flags, the opposite of the initial prompt, which is deliberately not re-sent. The review runs in a checkout that already exists and reaches the pull request through `gh`, so no branch moves under a working tree and a fork's head costs nothing extra; recipes live in `domain::pr_review` like `pr_task`, travel with the launch, and are never daemon state.
- An `AgentProfile.env` *is* an overlay, applied over the resolved environment after the terminal hints and before the daemon injects `FORGE_*`. `domain::RESERVED_PROFILE_VARS` may never come from a profile: the builder drops them, and `SaveAgentProfile` refuses to store them. A profile with its own `executable` is version-probed when saved, so no unprobed binary ever launches.
- SQLite migrations are embedded in `crates/persistence/src/migrations.rs`; append new migrations and never edit or reorder existing ones. Persistence stores metadata only, never terminal streams or runtime-only `TerminalId`s.
- On startup the daemon drops every session row (`Db::purge_sessions`), so the app opens on a clean tree; `sessions.persist_history = true` keeps them and reconciles the live ones to `Orphaned` instead. Tests that assert what survives a restart must boot with `Harness::boot_with(keep_history)`.
- Cost is an invariant here, not a tuning exercise: `docs/performance.md` carries the rungs, the rules and the defect behind each one. Three that bind every change. **Nothing that scales with the grid is deep-cloned on the delta rung** — it ships as `Arc`, and a queue that can be produced into faster than it is drained is bounded and drops, the way `registry.rs` already does with `flume::bounded(256)` plus a fresh resync for a `behind` client. **Per-cell code allocates nothing and locks nothing** — push the `CompactString`'s `&str`. **Anything derivable from the store is computed when the store changes**, never per frame.
- Every byte count that arrives from the wire, a subprocess, a file or the network is clamped **before** the allocation, never after: `PtySize::sanitized()` exists because an unclamped `65535×65535` resize asked for ~170 GB under the core lock. The budget-after-the-fact shape (`MAX_DIFF_BYTES` consulted once the whole patch is already resident) bounds the response and not the peak. Copy the four patterns that get it right — length checked against `MAX_FRAME_SIZE` before reserving, `metadata()` before `File::open`, a reader wrapped in `.take(cap)`, checked arithmetic on a client-supplied offset — and report `skipped`/`truncated` rather than looking exhaustive.
- A sleep-and-check loop is a defect unless it waits on something that cannot wake it (`reap_child`'s `WNOHANG` poll, `kill_groups_blocking`'s grace); `pty_loop` blocking in `poll(2)` until input or a deadline is the reference. Read "never hold the core lock across `.await`" as the stronger thing it means: never hold it across anything that can block — subprocess, network, filesystem walk or disk I/O. Every current exception carries a comment saying why; the two that remain (the session-title `upsert` in `pump_terminal`, and `resolved_env` lazily running `$SHELL -l -c 'env -0'` behind `&mut Inner`) are known debts, not precedent. `PRAGMA synchronous = NORMAL` is deliberate and correct under WAL — do not "fix" it back to the default.
- Every `Command` that can time out is built with `.process_group(0)` and killed with a **negative** pgid, with a direct-pid fallback: `wait_with_output()` drains both pipes to EOF before it waits, so killing the direct child leaves a grandchild (`ssh` under `git`, `npm` under `sh`) holding the write ends — a blocked thread, two leaked fds, a permanent zombie, and the hung process still running. `git_service::run_gh` is the reference; `signal_group`/`group_alive` always take a negative pid. Every `spawn()` is reaped, because `Child::drop` does not wait, and an unbounded `wait()` on the calling thread is its own bug — bound it with `try_wait` to a deadline and delegate, as `reap_child` does. State that must be unwound on a failure path (`fetching`, `pr_refreshing`, `pr_opening`) is unwound by a `Drop` impl, because `Daemon::lock` recovers from poisoning and a panicked worker otherwise latches the flag forever.
- A mutation that mints an id returns the id (`Response::SessionCreated` carries `session_id` **and** `terminal_id`), so a caller never reloads a snapshot to guess what it just created; that single `Ack` dragged a 201 MB transcript rescan and two sequential un-pooled HTTPS calls onto every <kbd>Cmd</kbd>+<kbd>T</kbd>. A convenience wrapper must not smuggle in a network call, a TTL shorter than the gap between two user actions is not a cache, and a cache key is fingerprinted from its **inputs**, never from the resolved output it was supposed to avoid computing.
- Before optimizing against a dependency's behaviour, read that dependency's source under `~/.cargo/registry/src/`. The whole-grid delta on every line feed looks narrowable via `scrolled_lines`; it is not, because `Term::damage()` returns early with `TermDamage::Full` and the per-line damage a mid-screen edit carried in the same chunk is then unreachable. `scripts/dev check` is the gate for correctness, not for cost, and would not have caught a single finding in `docs/performance.md`.

## Harness

- How to run it day-to-day: `docs/harness.md`. Human CLI: `scripts/harness status|list|show|resume|timeline|event|from-issue|next|root|validate|gate`. Skills: `/feature` → spec + human gate; `/feature-go` → implement + review; `/feature-status` → cheap read; `/feature-commit` → optional committer. Invariant skills `invariant-c4/c5/c7` assist the reviewer on boundary, runtime, and cost checks.
- `./init.sh` (also `scripts/harness gate`) is the harness gate: environment, base files, `harness/features.json` coherence, then `scripts/dev check`. `./init.sh --fast` / `scripts/harness gate --fast` skips only the cargo block and is what the Claude hooks run; closing a feature needs the full one.
- `harness/features.json` is the state machine (`pending → spec_ready → in_progress → in_review → done | blocked`), one active feature **per checkout** — worktrees of the same project run in parallel and share one `features.json` — validated by `harness/src/validate.ts`. Each step (spec → gate → implement → review) runs as a **headless job** (`claude -p`, `codex exec`) that the daemon starts and reaps: the cycle advances on exit codes, not on someone watching a terminal, and stops only at the human gate. Specs live in `harness/specs/<id>-<slug>/`, every subagent report in `harness/progress/`. `features.json`, `specs/<id>-<slug>/` and `progress/` are one developer's local state and gitignored; only the tooling (`src/`, `test/`, `CHECKPOINTS.md`, `specs/README.md`) is committed.
- Subagents write to disk and return one line with the path; the leader never receives diffs or findings in chat. `.claude/agents/reviewer.md` deliberately has no `Write`/`Edit`. Per-feature `events_<id>.jsonl`, `gate_<id>.md`, and `context_<id>.md` are required artefacts (see `docs/harness.md`). In Cursor they are Task `subagent_type`s: `spec-author`, `implementer`, `reviewer`, `committer`.
- `harness/CHECKPOINTS.md` C4-C5 restate the invariants in this file as reviewable checkboxes. When an invariant changes here, change it there.
- The harness never commits, pushes, or adds a dependency: it leaves a reviewable diff in the working tree.
